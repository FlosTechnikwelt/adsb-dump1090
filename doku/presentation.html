Was ist ADS-B?

  • Automatic Dependent Surveillance - Broadcast
  • Flugzeuge senden regelmaessig Daten ueber ihre Position und Bewegung
  • Ein Signal kann von vielen Empfaengern gleichzeitig gelesen werden
  • Die Daten sind offen und folgen einem festen Standard
  • Wichtige Felder: HEX, Flugnummer, Position, Hoehe, Geschwindigkeit
  • Je nach Empfang kann die Datenqualitaet besser oder schlechter sein
Flugzeug sendet regelmaessig offene ADS-B Daten.
Fokus: GrundverstaendnisSlide 3

Wie funktioniert ADS-B?

  • Sensoren im Flugzeug liefern die aktuellen Flugdaten
  • Der Transponder sendet diese Daten per Funk (meist 1090 MHz)
  • Bodenstationen und andere Empfaenger lesen die Signale
  • Ein Server wandelt die Signale in nutzbare Daten um
  • ADS-B Out bedeutet senden, ADS-B In bedeutet empfangen
Der Datenweg: Flugzeug -> Empfaenger -> Server -> Website.
Technischer AblaufSlide 4

Wer nutzt ADS-B?

  • Flugsicherung: sieht Flugzeuge im Luftraum besser
  • Airlines: behalten ihre Flotte und Ankunftszeiten im Blick
  • Flughaefen: planen Ankunft und Abflug genauer
  • Forschung und Behoerden: analysieren Verkehr und Sicherheit
  • Community: nutzt die Daten fuer Lernen und Spotting

GesamtsystemSlide 6

Datenfluss

  1. Das Frontend ruft regelmaessig /api/aircraft auf
  2. Der Server holt aktuelle ADS-B Daten von der Quelle
  3. Bekannte Zusatzdaten kommen aus Cache und Datenbank dazu
  4. Die Antwort geht sofort zurueck an das Frontend
  5. Speichern und weitere Anreicherung laufen im Hintergrund
  6. Karte, Popups und Statistiken werden aktualisiert
PipelineSlide 7

Backend: Kernlogik

  • recordAircraftData() speichert neue Sichtungen
  • Ein Zeitfenster verhindert zu viele doppelte Eintraege
  • Externe Aufrufe haben Timeouts, damit nichts haengen bleibt
  • Bekannte Zusatzdaten bleiben bei jedem Update erhalten
  • Der Server startet erst, wenn die Datenbank bereit ist
server.jsSlide 8

Anreicherung

  • Wir holen Bilder von planespotters.net
  • Typ und Hersteller kommen von hexdb.io
  • Externe Anfragen laufen nur, wenn Daten noch fehlen
  • Bekannte Daten werden im Cache gespeichert
  • So bleibt die Anzeige stabil und schneller
Mehr Kontext pro SichtungSlide 9

Datenbank

  • Die Daten liegen in der Datei stats.db
  • Die Tabelle aircraft_history sammelt alle Sichtungen
  • Zu jeder Sichtung speichern wir Zeit und Flugdaten
  • Auch Bild-URL, Typ und Hersteller werden gespeichert
  • Darauf bauen Suche und Statistiken auf
SQLite speichert Sichtungen als Basis fuer Analyse und Suche.

BetriebsaspekteSlide 13

DB-Problem: SQLITE_READONLY

  • Fehler nach Neustart: attempt to write a readonly database
  • Ursache 1: Server startete manchmal zu frueh
  • Ursache 2: Rechte von Datei/Ordner waren nicht korrekt
  • Der Fehler kam erst spaet beim Speichern
  • Das machte den Betrieb unzuverlaessig
DB-problem.mdSlide 14

DB-Fix und Wirkung

  • initDb() muss fertig sein, bevor der Server startet
  • ensureDbWritable() prueft Schreibrechte vor dem Start
  • Der DB-Pfad kann ueber DB_PATH eingestellt werden
  • Tippfehler wurde korrigiert: alt_bar zu alt_baro
  • Ergebnis: stabilerer Start und klare Fehler frueh im Prozess
  • Wichtig: Server nicht gemischt mit und ohne sudo starten
Vom Fehlerbild zur stabilen Loesung.
database.js + server.jsSlide 15

Planespotters-Problem: Bild verschwindet

  • Das Flugzeugbild war oft nur kurz sichtbar
  • Die Rohdaten enthalten meistens kein Bild
  • Durch Dedupe fehlte ein stabiles Zusammenfuehren der Zusatzdaten
  • Ein Update hatte Bild, das naechste wieder nicht
  • Die Anzeige wirkte dadurch unruhig und unklar
planspotter-problem.mdSlide 16

Planespotters-Fix und Wirkung

  • Metadaten werden pro HEX im Speicher zwischengespeichert
  • Bekannte Daten werden vor der Antwort aus der DB geladen
  • Die API antwortet schnell, Zusatzdaten kommen im Hintergrund
  • Externe Dienste werden nur bei fehlenden Daten gefragt
  • Bekannte Bilder bleiben jetzt stabil sichtbar
  • Nur bei ganz neuen HEX kann das Bild kurz spaeter kommen
